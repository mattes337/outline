# Task Management - Technical Specification

## 1. Overview

This document provides a technical specification for the Task Management feature in Outline. This feature allows users to create, track, and manage tasks that are embedded within documents. These tasks are synchronized with a central task management system, accessible via dedicated task views and a detailed task page. The system supports task creation via Markdown, synchronization with the database, API endpoints for management, and updates to document content when tasks are changed externally.

## 2. Database Schema

The task management feature introduces two new models: `Task` and `TaskComment`.

### 2.1 `Task` Model

*   **Table Name:** `tasks`
*   **Description:** Represents an individual task item. Each task is linked to a specific document and can be assigned to a user.

*   **Attributes:**
    *   `id: UUID` - Primary key, auto-generated (UUIDv4).
    *   `guid: UUID` - Global unique identifier, typically generated by the client (Prosemirror node). Used for consistent referencing between document content and the database. Unique per document (`documentId`, `guid`).
    *   `documentId: UUID` - Foreign key referencing `documents.id`. Indicates the document this task belongs to.
    *   `userId: UUID | null` - Foreign key referencing `users.id`. Represents the assignee of the task. Can be `null` if unassigned.
    *   `title: TEXT` - The main descriptive text of the task.
    *   `body: TEXT | null` - A longer, optional Markdown-formatted description or details for the task.
    *   `status: STRING` - The current status of the task. Common values: "open", "completed", "orphaned". Defaults to "open".
    *   `priority: INTEGER` - An integer used for ordering tasks, especially in user-facing lists. Lower numbers typically indicate higher priority. Defaults to 0.
    *   `createdAt: DATE` - Timestamp of creation.
    *   `updatedAt: DATE` - Timestamp of last update.

*   **Relations:**
    *   `belongsTo Document` (aliased as `document`)
    *   `belongsTo User` (aliased as `assignee`)
    *   `hasMany TaskComment` (aliased as `comments`)

*   **Indexes:**
    *   `guid`
    *   `documentId`
    *   `userId`
    *   `status`
    *   Composite unique index on `(documentId, guid)`

### 2.2 `TaskComment` Model

*   **Table Name:** `task_comments`
*   **Description:** Represents a comment made on a specific task.

*   **Attributes:**
    *   `id: UUID` - Primary key, auto-generated (UUIDv4).
    *   `taskId: UUID` - Foreign key referencing `tasks.id`. Indicates the task this comment belongs to.
    *   `userId: UUID` - Foreign key referencing `users.id`. The author of the comment.
    *   `content: TEXT` - The textual content of the comment (can be Markdown).
    *   `createdAt: DATE` - Timestamp of creation.
    *   `updatedAt: DATE` - Timestamp of last update.

*   **Relations:**
    *   `belongsTo Task` (aliased as `task`)
    *   `belongsTo User` (aliased as `user` or `author`)

*   **Indexes:**
    *   `taskId`
    *   `userId`

## 3. Editor Integration - Prosemirror `TaskItem` Node

Tasks are represented within documents using a custom Prosemirror node.

*   **Node Name:** `task_item`

*   **Attributes:**
    *   `guid: string` - A client-generated UUID (v4) that uniquely identifies the task within the document and for backend synchronization.
    *   `checked: boolean` - Represents the completion status of the task (`true` for completed, `false` for open).

*   **Content Specification:** `inline*`
    *   Allows any inline content (text, links, emphasis, etc.) as the task's title/description directly within the node.

*   **Markdown Serialization Format:**
    *   The node serializes to a custom Markdown format: `[task:{guid}] [{checked ? 'x' : ' '}] {content}`
    *   Example (unchecked): `[task:abc-123] [ ] This is a task title`
    *   Example (checked): `[task:def-456] [x] This task is done`

*   **Markdown-it Plugin (`rulePlugins` in `TaskItemNode.ts`):**
    *   A custom markdown-it block rule is implemented to parse both the custom `[task:{guid}]...` format and standard GitHub Flavored Markdown (GFM) task lists.
    *   **Custom Format Parsing:** The plugin uses a regex (`/^\s*\[task:([0-9a-fA-F-]+)\]\s*\[( |x)\]\s*(.*)/`) to identify and extract the `guid`, `checked` state, and `content` from the custom task syntax.
    *   **GFM Format Parsing:** It also uses a regex (`/^\s*(?:[-*+]|\d+\.)\s*\[( |x)\]\s+(.*)/`) to identify GFM task list items (e.g., `- [ ] Task`, `* [x] Task`).
        *   For GFM tasks, a new `guid` is generated (using `uuidv4()`) as GFM does not have an inherent GUID.
    *   The plugin modifies the markdown-it token stream, typically by decorating `list_item` tokens with metadata (`taskGuid`, `taskChecked`, or a direct `checked` boolean for GFM). This metadata is then used by the `parseMarkdown.getAttrs` function of the `TaskItemNode` to correctly instantiate the Prosemirror node with the necessary attributes.
    *   The rule is registered to run before the default `list` rule in markdown-it's block ruler to ensure it correctly processes task lines.

*   **Input Rule:**
    *   An input rule is defined for the pattern `^\s*(\[ \])\s$`.
    *   When a user types `[ ] ` (followed by a space), this rule triggers.
    *   It creates a new `task_item` node with `checked: false` and a newly generated `guid` (using `uuidv4()`), replacing the typed pattern.

*   **React NodeView (`app/editor/components/TaskItemView.tsx`):**
    *   A React component is used to render the `task_item` node in the editor.
    *   This NodeView displays a checkbox (reflecting the `checked` attribute) and the inline content of the task.
    *   It handles user interaction with the checkbox: when clicked, it dispatches a Prosemirror transaction to update the `checked` attribute of the node in the editor state. This change is then picked up by the collaboration and persistence layers.

## 4. Backend Synchronization Logic

Synchronization ensures that tasks defined in documents are reflected in the `tasks` database table, and vice-versa (though direct document updates from DB changes are handled by a separate processor).

### 4.1 `TaskSyncProcessor.ts`

This processor is responsible for the primary synchronization from document content to the `tasks` database table.

*   **Events Handled:**
    *   `tasks.sync.request`: Triggered when a document is updated.
    *   `tasks.sync.execute`: The actual job that performs the synchronization.

*   **Debouncing Strategy:**
    *   When a `tasks.sync.request` event occurs (e.g., due to `Document.scheduleTaskSync` or direct calls from `documentUpdater`), the `TaskSyncProcessor` does not immediately sync.
    *   Instead, it enqueues a `tasks.sync.execute` job with a delay (default 30 seconds, configurable via `TASK_SYNC_DELAY_MS`).
    *   The `originalTimestamp` (usually `document.updatedAt` from the request event) is passed to the delayed job.
    *   When `tasks.sync.execute` runs, it first checks if the current `document.updatedAt` is newer than the `originalTimestamp`. If so, it means the document was modified again after the initial request, and a newer sync request would have been (or will be) enqueued. The current job then aborts to prevent race conditions and ensure only the latest state is processed.

*   **Core Logic of `tasks.sync.execute`:**
    1.  **Fetch Document Content:** Retrieves the specified `Document`, ensuring its Prosemirror state (`document.state` or derived from `document.content`) is available.
    2.  **Parse `task_item` Nodes:** Converts the document content to a Prosemirror node structure using `DocumentHelper.toProsemirror()`. It then traverses this structure using `node.descendants()` to find all `task_item` nodes. For each found node, it extracts:
        *   `guid` (from node attributes)
        *   `checked` state (from node attributes)
        *   `title` (from the `textContent` of the node, with potential cleanup of `[ ] ` prefixes).
    3.  **Compare with Database:**
        *   Fetches all existing tasks from the `tasks` table associated with the `documentId`.
        *   A `Map` of existing tasks (keyed by `guid`) is created for efficient lookup.
    4.  **Synchronization Rules (within a database transaction):**
        *   **New Tasks:** If a `guid` from a document task is not found in the `existingTasksMap`, a new `Task` record is created in the database with the extracted `guid`, `title`, and `status` (derived from `checked`).
        *   **Update Existing Tasks:** If a `guid` matches an existing task:
            *   The `title` is updated if it differs from the document task's title.
            *   The `status` is updated (`open` or `completed`) if the `checked` state differs.
            *   If an existing task had `status: "orphaned"` but is now found in the document, its status is updated to `open` or `completed`.
            *   If any changes are made, the `Task` record is saved.
        *   **Orphaned Tasks:** Any tasks in `existingTasksMap` that were not found (by `guid`) in the document content (i.e., not in `seenGuids`) and are not already marked as "orphaned" are updated to `status: "orphaned"`. This signifies that the task was removed from the document content.

### 4.2 Triggering Synchronization

Synchronization is primarily initiated when a document's content or relevant metadata changes.

*   **`documentUpdater.ts`:**
    *   After a document is saved via this command (typically used for non-collaborative updates or API-driven changes), if the `text` (Markdown content) or `title` has changed, it creates a `documents.update` event.
    *   It then calls `createdEvent.queue("tasks.sync.request", { documentId, timestamp })` to enqueue a sync request. This also occurs after a successful publish operation.

*   **`documentCollaborativeUpdater.ts`:**
    *   After collaborative changes are persisted and a `Document` is updated, it schedules a `documents.update` event.
    *   Similarly, it then calls `event.queue("tasks.sync.request", { documentId, timestamp })` to enqueue a sync request. The timestamp used is `new Date().toISOString()` as `document.updatedAt` might not be immediately up-to-date due to `hooks: false` during the update.

*   **`Document.scheduleTaskSync` Static Method (Intended as AfterUpdate Hook Logic):**
    *   This static method encapsulates the logic for deciding whether to trigger a task sync. It is intended to be used in contexts equivalent to an `AfterUpdate` hook on the `Document` model.
    *   It checks if `content`, `state`, or `title` changed using `instance.changed()`.
    *   If significant changes are detected and the document has an ID and `updatedAt` timestamp, it schedules a `tasks.sync.request` event and queues it.
    *   This ensures that direct model saves (outside of the specific updater commands) also trigger task synchronization if relevant fields change. It avoids self-triggering if the update was part of a `tasks.sync.execute` transaction.

## 5. API Endpoint Documentation

(Incorporating content from `docs/api-tasks.md`)

*   **Base URL:** All API endpoints are prefixed with `/api`.
*   **Authentication:** Requires a valid JWT token.

---

### 5.1 List My Open Tasks

*   **Endpoint:** `GET /tasks.my` (or `POST /api/tasks.my`)
*   **Description:** Fetches all open (uncompleted) tasks assigned to the currently authenticated user.
*   **Permissions:** Authenticated user.
*   **Request Body Parameters (if using POST):**
    *   `token: string` (required)
    *   Pagination parameters (optional, e.g., `offset`, `limit`).
*   **Example Successful Response (200 OK):**
    ```json
    {
      "data": [
        {
          "id": "task-uuid-1",
          "guid": "task-guid-abc",
          "title": "My first open task",
          "body": "Detailed description of the task.",
          "status": "open",
          "priority": 0,
          "createdAt": "2023-01-15T10:00:00.000Z",
          "updatedAt": "2023-01-15T10:00:00.000Z",
          "document": { /* ... document presenter fields ... */ },
          "assignee": { /* ... user presenter fields ... */ },
          "comments": []
        }
      ],
      "pagination": { "offset": 0, "limit": 25, "total": 1 }
    }
    ```

---

### 5.2 List All Open Tasks

*   **Endpoint:** `GET /tasks.open` (or `POST /api/tasks.open`)
*   **Description:** Fetches all open tasks for the user's team, ordered by priority.
*   **Permissions:** Authenticated user.
*   **Request Body Parameters (if using POST):** `token`, pagination.
*   **Response:** Similar structure to `/tasks.my`.

---

### 5.3 List Done Tasks

*   **Endpoint:** `GET /tasks.done` (or `POST /api/tasks.done`)
*   **Description:** Fetches all completed tasks for the user's team, ordered by update date (descending).
*   **Permissions:** Authenticated user.
*   **Request Body Parameters (if using POST):** `token`, pagination.
*   **Response:** Similar structure to `/tasks.my`.

---

### 5.4 Get Task Information

*   **Endpoint:** `GET /tasks.info` (or `POST /api/tasks.info`)
*   **Description:** Fetches details for a specific task by its GUID. Includes document, assignee, and comments.
*   **Permissions:** User must have access to the task's parent document.
*   **Request Body Parameters (if using POST):** `token`, `guid: string` (task GUID).
*   **Response:**
    ```json
    {
      "data": { /* Full Task object with associated document, assignee, and comments */ }
    }
    ```
*   **Errors:** 401, 403, 404 (task not found), 400 (invalid GUID).

---

### 5.5 Update Task

*   **Endpoint:** `PUT /tasks.update` (or `POST /api/tasks.update`)
*   **Description:** Updates properties of a specific task.
*   **Permissions:** Admin, task assignee, or user with edit rights on the parent document.
*   **Request Body Parameters (if using POST):**
    *   `token: string`
    *   `guid: string` (task GUID)
    *   `title?: string`
    *   `body?: string` (Markdown)
    *   `status?: "open" | "completed"`
    *   `priority?: integer`
    *   `userId?: string | null` (assignee's user ID, null to unassign)
*   **Response:** Updated Task object.
*   **Side Effect:** If `status` changes, enqueues a `tasks.update_document_node` job.
*   **Errors:** 401, 403, 404, 400 (invalid parameters).

---

### 5.6 Create Task Comment

*   **Endpoint:** `POST /tasks.createComment` (or `POST /api/tasks.createComment`)
*   **Description:** Adds a comment to a specific task.
*   **Permissions:** User must have access to the task.
*   **Request Body Parameters:**
    *   `token: string`
    *   `guid: string` (task GUID)
    *   `content: string` (comment text)
*   **Response:** Newly created TaskComment object.
*   **Errors:** 401, 403, 404, 400 (missing content).

---

### 5.7 Reorder Tasks

*   **Endpoint:** `PUT /tasks.reorder` (or `POST /api/tasks.reorder`)
*   **Description:** Updates the priority of multiple tasks based on their new order.
*   **Permissions:** Authenticated user.
*   **Request Body Parameters:**
    *   `token: string`
    *   `orderedGuids: string[]` (array of task GUIDs in the new order)
*   **Response:** `{ "success": true }`
*   **Errors:** 401, 400 (invalid input, or tasks from different teams/inaccessible).

## 6. Updating Document from Task Changes

When a task's status is changed via the API (e.g., from the Task Detail Page), the corresponding `task_item` node in the source document needs to be updated to reflect this change (e.g., checkbox ticked/unticked).

### 6.1 `TaskDocumentNodeUpdateProcessor.ts`

This processor handles this reverse synchronization (DB task change -> Document content update).

*   **Event Handled:** `tasks.update_document_node`
    *   This event is enqueued by the `/api/tasks.update` endpoint when a task's `status` is changed.
    *   Event data includes `taskId`, `documentId`, `newCheckedState`, and optionally `actorId`.

*   **Logic:**
    1.  **Load Data:** Fetches the `Task` (to get its `guid`) and the `Document`.
    2.  **Parse Document:** Converts the document content to a Prosemirror node tree using `DocumentHelper.toProsemirror()`.
    3.  **Find and Update Node:**
        *   Recursively traverses the Prosemirror node tree.
        *   It looks for a `task_item` node whose `guid` attribute matches the `task.guid`.
        *   If found, and its `checked` attribute differs from `newCheckedState`, it creates a new `task_item` node with the updated `checked` attribute, preserving other attributes and content. This marks the tree as `nodeUpdated`.
    4.  **Save Document:** If `nodeUpdated` is true:
        *   The modified Prosemirror tree is converted back to JSON content (`DocumentHelper.toProsemirrorJSON()`) and Markdown text (`DocumentHelper.toMarkdown()`).
        *   The `document.content` and `document.text` fields are updated.
        *   The `document.lastModifiedById` is set to the `actorId` (or a fallback).
        *   The document is saved within a new database transaction.
    5.  **Re-trigger Sync:** After successfully saving the document, it manually creates a `documents.update` event and queues a new `tasks.sync.request` for the updated document. This ensures that the main `TaskSyncProcessor` runs, which can be important for overall consistency and if other parts of the document were affected by model hooks during the save.

## 7. Frontend Overview (Brief)

*   **`app/scenes/TasksPage.tsx`:**
    *   **Purpose:** Provides a centralized view for users to manage their tasks.
    *   **Tabs:**
        *   "My Open Tasks": Tasks assigned to the current user, open status. Supports drag-and-drop reordering.
        *   "All Open Tasks": All open tasks in the team. Supports drag-and-drop reordering.
        *   "Done Tasks": Completed tasks in the team.
    *   **Data Fetching:** Fetches tasks for the active tab using methods from `TasksStore` (which call the relevant API endpoints).
    *   **Reordering:** Handles `onReorder` from `TaskList` component, calls `tasksStore.reorderTasks` (which calls `/api/tasks.reorder`), and optimistically updates local state.

*   **`app/scenes/TaskDetailPage.tsx`:**
    *   **Purpose:** Displays and allows editing of a single task's details.
    *   **Data Display & Editing:**
        *   Title (inline editable).
        *   Assignee (selectable, uses a basic select as placeholder for `UserSelect`).
        *   Status (toggle button: "Mark as Complete" / "Re-open Task").
        *   Document Link.
        *   Priority (display only).
    *   **Body Editor:** Uses a Prosemirror `Editor` component for the task's Markdown body. Edits are saved on blur/save action. Read-only for completed tasks.
    *   **Comments:** Lists existing comments and provides a form to add new comments.
